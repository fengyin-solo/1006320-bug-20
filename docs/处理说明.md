# 存量缺陷修复处理说明

本说明对应「廊内环境监测确认正常后异常数不回落」「重复上报」「往期巡检搬入」「审批结论同步交接清单」四条链路的修复口径，代码实现与本文档一致。文档同时由「廊内环境监测」「廊内巡检任务」页面内的说明摘要引用。

## 1. 廊内环境监测：确认正常链路

### 1.1 现象与根因

- 确认正常只改了记录状态，超标标记（`abnormal`）与另存清单里的超标残留没有一起改写。
- 概览超标数按记录累加，没有按监测点位去重重算，同一点位确认后数字不减；再点一次确认还会再减一回。
- 氧气浓度在概览里另算一遍，与温湿度判定口径不一致。
- 页面统计卡写死为 0；点按钮失败时错误信息只在页脚，表现为「点下去没反应」。

### 1.2 统一判定口径（唯一来源）

判定函数：`src/domain/env.ts` 的 `evaluateReading(row)`，列表、详情、概览、导出 CSV、动作流转、存量回填全部调用它，概览不允许另算。

| 指标 | 字段 | 正常区间 | 单位 |
| --- | --- | --- | --- |
| 环境温度 | 环境温度 | 5 ~ 32 | ℃ |
| 空气湿度 | 空气湿度 | 0 ~ 85 | %RH |
| 氧气浓度 | 氧气浓度 | 19.5 ~ 23.5（低于下限为缺氧，高于上限为富氧） | %VOL |
| 有害气体浓度 | 有害气体浓度 | 0 ~ 10 | ppm |

取值解析：从字符串中提取第一个数值（如 `"24.6℃"` → `24.6`）；空串、非数值、占位文本（含「样例」）一律视为**未采集**。

### 1.3 写入规则（监测记录与超标标记一起改写）

- 「提交采集」：四项取值齐全才允许落库，落库时按 `evaluateReading` 一次性写入 `状态 / pending / abnormal / 超标判定 / 超标原因 / 采集时间 / 备注`；取值不全直接拒绝，不留半截。
- 「确认正常（判定正常）」：
  - 取值未采集完整：拒绝；
  - 按口径实测仍超标：拒绝，禁止状态与数值两张皮；
  - 已是「指标正常」且 `abnormal=false`：**幂等返回**，任何计数都不再变化（修复重复点再减一次）；
  - 其余：记录与超标标记一起改写为正常结论。
- 「标记超标」：仅当按口径实测超标时允许，记录、`abnormal`、超标原因一起改写。

### 1.4 超标点位数：按监测点位重算，不累加

`envMetrics(rows)` 规则：

1. 同一「监测点位」只取「采集时间」最新的一条记录作为点位现状；
2. 超标点位数 = 现状为「指标超标」或按口径判定超标的**不同点位**数；
3. 待采集点位、正常点位同理按点位去重；
4. 概览（`loadOverview`）、环境监测页统计卡读同一个 `envMetrics`，概览不再单独对氧气另算。

### 1.5 同一份数据

- 列表/详情：`listEntries` / `getEntry` 读同一份 localStorage 台账；
- 导出 CSV：列含「超标判定、超标原因、备注」，直接导出台账当前值，历史超标标记不残留；CSV 单元格做转义；
- 概览：见 1.4；
- 存储层：单模块写入与跨模块写入都先序列化整库落 localStorage，失败时回滚快照，字段没落库的不留在中间态（见第 5 节）。

### 1.6 存量监测记录回填（按采集时间）

迁移：`src/data/migrations.ts`（数据版本 v1 → v2，幂等，已打 `数据版本=2` 的不再处理）。

- 所有环境记录先按「采集时间」升序排列后逐条回填。
- **早年把「未采集」写成「指标正常」的区分方式（已定口径）**：四项取值中任何一项解析不出数值，就不承认其为正常——
  - 状态退回「待采集」，`pending=true`、`abnormal=false`、超标判定写「未采集」；
  - 备注注明：`存量回填(采集时间)：<缺失项>，原状态「指标正常」不成立，退回待采集`；
  - 不猜测、不内插历史取值，由人工重新采集。
- 四项齐全的老记录按 1.2 阈值统一重判：状态、超标标记、超标原因一并改写；原「正常」复核超标或原「超标」复核正常的，在备注写明已纠正。
- 「采集时间」本身缺失的，不臆造时间，备注「缺采集时间，待人工确认」，排序时按空值处理。

## 2. 入廊作业审批结论 → 值班交接清单

- 动作修正为「批准申请 / 驳回申请 / 完工确认」（原元数据里「提交审批→已批准、确认批准→已驳回、驳回申请→已完工」指向错误）。
- 审批动作通过 `commitRows` 同时写两张表：作业申请（状态、审批结论、备注）与值班交接清单；任一落库失败两处一起退回。
- 交接清单载体：系统按日期自动维护一条 `AUTO-DUTY-YYYY-MM-DD` 的值班交接记录，审批结论写在其「交接事项」中，格式：
  `【作业审批】申请编号｜结论｜时间｜申请单位/舱室/类型与结论文本`
- **同一申请编号只保留一条**（upsert），重复审批覆盖旧结论行而不是追加。
- 入廊作业审批页与运维值班交接页都通过 `approvalHandoverLines()` 读同一份内容，两处展示一致。

## 3. 廊内巡检：重复上报与往期搬入

### 3.1 重复上报只认第一次

`reportIssue(current, payload)`：

- 首次上报：写入「上报问题、上报明细」，状态置「已上报」，`上报次数=1`，首报内容锁定；
- 再次上报：首报字段**一律不覆盖**。与首报有差异的，差异内容（问题文本/明细文本）追加到「备注」，格式 `重复上报(时间)：……，以首次上报为准`；内容一致也记一条「内容一致」备注，`上报次数+1`。

### 3.2 往期数据按巡检日期整体搬入

入口：巡检页「往期数据搬入」。支持 CSV/TSV，可带表头（表头含「巡检编号」），无表头时按固定列序：

`巡检编号、巡检路线、巡检班组、巡检日期、计划日期、完成时间、发现问题数、巡检人员、巡检状态`

流程为「解析 → 预案（不落库） → 人工核对 → 整套提交」：

- **缺失项处理方式（已定口径）**：不臆造、不内插、不用默认值冒充真实数据。
  - 「发现问题数」缺失：暂记 0，但仍列入缺失清单（标注「原值不可解析，暂记0」），状态置「待确认」，备注列明缺失字段；
  - 其余字段（路线/班组/巡检日期/计划日期/完成时间/巡检人员）缺失：留空，写入「缺失字段」，状态「待确认」，`pending=true`，逐条列在导入预案与列表标签里，等人工「补录确认」；
  - 人工补录全部缺失字段后任务回到「待巡检」，进入正常流转；仍有缺项则保持「待确认」。
- 「巡检状态」不可识别的按「待巡检」处理，缺字段时仍优先挂「待确认」。
- 巡检编号在文件内重复、或行内无巡检编号：阻断该行并给出原因，不进预案。
- 入库顺序：预案按「巡检日期」升序排序后整体写入。
- **与台账现状一致**：同巡检编号已存在时，台账已有字段值保持不变，导入值与台账的差异逐条写入备注（不覆盖），缺失项同样挂「待确认」。
- 「导入明细与台账现状保持一致」的核对：入库返回逐行对账结果（新增/对齐、差异条数、缺项情况），在页面「入库对账」区展示。

### 3.3 整套退回

`commitPatrolImport` 只调用一次 `saveRows('patrol', rows)`；存储层先整库落 localStorage、失败恢复快照并抛错，错误向上传递为「导入落库失败，整套已退回」。预案阶段从不修改台账，因此不存在「字段没落库但留在中间态」。

## 4. 落库失败整套退回（存储层）

`src/data/local-store.ts`：

- `saveRows(key, rows)` / `commitRows(next)` 统一走 `persist`：保存 `localStorage` 快照 → 写整库数据与版本元信息 → 任一步抛异常则用快照恢复（含删除本次新建的键）→ 再抛错；
- 缓存只在落库成功后更新，失败时内存与浏览器存储都维持原状；
- 环境监测的「提交采集/确认/标记」、巡检导入、审批×交接跨表写入都在此约束内。

## 5. 数据版本与重置

- 版本键：`urban-utility-tunnel:meta = { version: 2 }`，数据键不变：`urban-utility-tunnel:entries`。
- 老用户打开时按 v1 数据执行一次回填并尝试升级落库；升级落库失败不丢内存数据，下次打开重试。
- 想回到示例数据：清掉上述两个 localStorage 键，或调用 `resetModule(模块)`（重置后同样按 v2 口径迁移）。
